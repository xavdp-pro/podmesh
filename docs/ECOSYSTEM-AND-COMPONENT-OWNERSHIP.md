# PodMesh in the SHAPER ecosystem

## Useful role in the human–AI tandem

PodMesh supplies typed infrastructure operations, placement, movement, storage
and recovery capabilities. The human–AI tandem supplies intention and mandate.
A governor maintains approved desired state for its declared scope; a maker
materializes permitted changes. PodMesh executes delegated technical operations
and reports attributable results. An infrastructure manager's name does not make
it a business governor or a source of permission.

The [ecosystem](https://github.com/xavdp-pro/shaper-ecosystem) owns composition
and cross-project task routes. The [independent glossary](https://github.com/xavdp-pro/shaper-glossary)
owns definitions and historical aliases. OS, Runtime and Workspace describe
responsibilities; component, stem cell, specialized service, logical space and
fractal describe composition. A space groups service membership and jurisdiction
independently of placement. PodMesh can also be used standalone.

## Reusable forms and identified services

A class has an owner, version and interface/configuration contract. A reusable
specialization composes a base with domain capability. An instance binds the
selected form to a stable identity, private configuration/state and jurisdiction.
Host movement preserves that identity. The
[class/instance contract](https://github.com/xavdp-pro/shaper-ecosystem/blob/main/chapters/20-CLASS-INSTANCE.md)
and [local-to-production journey](https://github.com/xavdp-pro/shaper-ecosystem/blob/main/chapters/09-LOCAL-TO-PRODUCTION.md)
connect local Linux, macOS and Windows development profiles to selected production
hosting through explicit provider capabilities.

## Application state and continuity

[Functional unit ownership](FUNCTIONAL-UNITS.md) retains the selected private
MariaDB profile for declared durable node and manager components. All durable
application state has an owner, transaction boundary, retention/partition policy,
identity and capture/restore contract. Partition according to actual workload and
maintenance needs. A derived search index, when selected, retains source
provenance and a rebuild path to authoritative application facts.

MariaDB continues the stable Turbinobash noweb operating foundation: familiar
maintenance, backups and predictable restoration. Component-owned state localizes
failure; service and infrastructure coordination supply distributed redundancy,
continuity and disaster recovery. This does not require a complex SQL cluster
inside each component. See the
[shared rationale](https://github.com/xavdp-pro/shaper-ecosystem/blob/main/chapters/32-PERSISTENCE-AND-RECOVERY-RATIONALE.md).

Typed requests preserve operation identity, authority and observed outcomes.
Declared source capture, state transfer, restore and promotion boundaries remain
explicit. [Source/host separation](HOST-ADAPTER-CONTRACT.md) keeps privileged
technical capability apart from application identity and governance.

## Source custody and compatibility

PodMesh maintains its existing public product/private workshop split: reusable
product interfaces and code belong here; private topology, dialogue, current
campaign state and concrete evidence belong to its companion workshop. Generic
public mental sources do not publish commercial VOX or user SaaS implementations.
Each concerned project keeps a distinct source repository and work/discussion lab.

Use component in current conceptual presentation. Existing `podmesh-node`,
`podmesh-manager`, image/API/storage identifiers and historical FUnit/brick paths
remain compatible until their owners define an explicit transition. The
framework adoption pin in [AGENTS.md](../AGENTS.md) remains a distinct versioned
record; source navigation updates do not migrate a running realization.
