## MeshFS opt-in cluster implementation (2026-10-20)

MeshFS now has an explicit fixed-membership cluster mode with quorum-committed
mutations, durable logs, leader-barrier reads and snapshot-based replica
catch-up. Discovery-only peer lists do not establish replication. Existing
standalone storage is not migrated implicitly. See [MESHFS-CLUSTER.md](MESHFS-CLUSTER.md)
for startup, security boundaries and operational limitations. Large offline VM images now use a bounded-block streaming API and CLI, with
file-backed snapshot transfer. The compatibility JSON endpoint remains limited
to small payloads. Live VM block access, safe membership replacement and
production operations require separate implementation and qualification. This
is not a production certification or an installed service cutover. Detailed campaign evidence belongs to the private workshop.

## 2026-10-20 — experimental live MeshFS access

An opt-in synchronous FUSE adapter is now implemented alongside the existing
large-file streaming interface. Its deliberately restricted contract, digest
formats, failover deadline and single-writer requirement are described in
[MESHFS-LIVE-ACCESS.md](MESHFS-LIVE-ACCESS.md). Qualification receipts belong to
the private workshop. This does not add VM orchestration to PodMesh or qualify
the Proxmox plugin, complete POSIX semantics, fencing or production HA.


## Experimental recovery boundary

The live adapter's documentation explicitly distinguishes idempotent retries
from cancellation and writer-session fencing. A bounded process-recovery proof
does not establish power-loss, delayed-request, multi-writer or general release
qualification. See [MESHFS-LIVE-ACCESS.md](MESHFS-LIVE-ACCESS.md).

## Immutable live mutation preconditions

Live mutations now retain their original source and rename-destination versions
across retries. Durable revisions prevent delete/recreate version reuse, and
legacy uploads cannot replace live inodes. The protocol boundary, uncertain
outcomes and remaining single-writer limitations are documented in
[MESHFS-LIVE-ACCESS.md](MESHFS-LIVE-ACCESS.md). This changes the experimental
protocol; it does not qualify mixed-version upgrades or production storage.

## New-protocol restore boundary

External, quiesced backup and empty-target restore must include exact artifact
identity, byte equality before application start, unavailable source endpoints,
and useful restored VM/container operation. This acceptance scope is distinct
from PMBS integration, live backup consistency, peer snapshot transfer and
mixed-version upgrades. Detailed candidate receipts remain in the private
workshop. The public guide's external home link opens a separate browser tab.

## PMBS canonical upload boundary

The pre-correction PMBS HTTP chunk path rejected its canonical 4 MiB input
before storage. Its chunk-integrity verifier also could not be treated as actual
sandbox boot proof. The implementation/design and acceptance boundaries are explicit in
[BACKUP-SERVER.md](BACKUP-SERVER.md). No PMBS restore readiness follows from
separate external-backup acceptance.

## PMBS canonical input and truthful verification

The chunk upload route now accepts the canonical4MiB payload with a strict
upper bound; JSON limits remain separate. Referenced-chunk integrity is reported
without claiming a sandbox boot. API-driven snapshot backup/retrieval and
independent restored-workload operation remain explicit acceptance steps,
distinct from a native automated restore command. See
[BACKUP-SERVER.md](BACKUP-SERVER.md) for the supported boundary.

## PMBS manifest and API policy

Snapshot publication now validates structure, referenced content and complete
file hashes; committed snapshot identities cannot be replaced. Storage names,
logical paths and chunk IDs are bounded. HTTP requires an administrative bearer,
default binding is loopback, and local IPC is owner-only. Arbitrary-URL HTTP sync
is disabled and status reports it disabled. See [BACKUP-SERVER.md](BACKUP-SERVER.md)
for compatibility changes and the trusted TLS/local-storage boundary. Previous
restore receipts remain attached to their own artifacts; policy qualification
is separate from a new full recovery campaign.
