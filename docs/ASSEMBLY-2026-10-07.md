## MeshFS opt-in cluster implementation (2026-10-20)

MeshFS now has an explicit fixed-membership cluster mode with quorum-committed
mutations, durable logs, leader-barrier reads and snapshot-based replica
catch-up. Discovery-only peer lists do not establish replication. Existing
standalone storage is not migrated implicitly. See [MESHFS-CLUSTER.md](MESHFS-CLUSTER.md)
for startup, security boundaries and operational limitations. Large offline VM images now use a bounded-block streaming API and CLI, with
file-backed snapshot transfer. The compatibility JSON endpoint remains limited
to small payloads. Live VM block access, safe membership replacement and
production operations require separate implementation and qualification. This
is not a production certification or an installed service cutover. Detailed campaign evidence belongs to the private workshop.

## 2026-10-20 — experimental live MeshFS access

An opt-in synchronous FUSE adapter is now implemented alongside the existing
large-file streaming interface. Its deliberately restricted contract, digest
formats, failover deadline and single-writer requirement are described in
[MESHFS-LIVE-ACCESS.md](MESHFS-LIVE-ACCESS.md). Qualification receipts belong to
the private workshop. This does not add VM orchestration to PodMesh or qualify
the Proxmox plugin, complete POSIX semantics, fencing or production HA.


## Experimental recovery boundary

The live adapter's documentation explicitly distinguishes idempotent retries
from cancellation and writer-session fencing. A bounded process-recovery proof
does not establish power-loss, delayed-request, multi-writer or general release
qualification. See [MESHFS-LIVE-ACCESS.md](MESHFS-LIVE-ACCESS.md).

## Immutable live mutation preconditions

Live mutations now retain their original source and rename-destination versions
across retries. Durable revisions prevent delete/recreate version reuse, and
legacy uploads cannot replace live inodes. The protocol boundary, uncertain
outcomes and remaining single-writer limitations are documented in
[MESHFS-LIVE-ACCESS.md](MESHFS-LIVE-ACCESS.md). This changes the experimental
protocol; it does not qualify mixed-version upgrades or production storage.

## New-protocol restore boundary

External, quiesced backup and empty-target restore must include exact artifact
identity, byte equality before application start, unavailable source endpoints,
and useful restored VM/container operation. This acceptance scope is distinct
from PMBS integration, live backup consistency, peer snapshot transfer and
mixed-version upgrades. Detailed candidate receipts remain in the private
workshop. The public guide's external home link opens a separate browser tab.

## PMBS canonical upload boundary

The pre-correction PMBS HTTP chunk path rejected its canonical 4 MiB input
before storage. Its chunk-integrity verifier also could not be treated as actual
sandbox boot proof. The implementation/design and acceptance boundaries are explicit in
[BACKUP-SERVER.md](BACKUP-SERVER.md). No PMBS restore readiness follows from
separate external-backup acceptance.

## PMBS canonical input and truthful verification

The chunk upload route now accepts the canonical4MiB payload with a strict
upper bound; JSON limits remain separate. Referenced-chunk integrity is reported
without claiming a sandbox boot. API-driven snapshot backup/retrieval and
independent restored-workload operation remain explicit acceptance steps,
distinct from a native automated restore command. See
[BACKUP-SERVER.md](BACKUP-SERVER.md) for the supported boundary.

## PMBS manifest and API policy

Snapshot publication now validates structure, referenced content and complete
file hashes; committed snapshot identities cannot be replaced. Storage names,
logical paths and chunk IDs are bounded. HTTP requires an administrative bearer,
default binding is loopback, and local IPC is owner-only. Arbitrary-URL HTTP sync
is disabled and status reports it disabled. See [BACKUP-SERVER.md](BACKUP-SERVER.md)
for compatibility changes and the trusted TLS/local-storage boundary. Previous
restore receipts remain attached to their own artifacts; policy qualification
is separate from a new full recovery campaign.

## Empty-replica catchup with mutation preconditions

Qualification of a fresh replacement for a stopped, same-identity replica must
verify actual snapshot installation after journal purge, local CAS data, durable
inode/global revisions and semantic retry metadata. A successful forwarded read
is insufficient. Exact retries must preserve newer bytes, obsolete preconditions
must fail, and a useful new mutation must converge after recovery. This scope is
distinct from admitting a new member, fencing duplicate identities, upgrades or
HA. Detailed candidate receipts remain in the private workshop.


## Replay metadata retention boundary

The v3 protocol carries immutable replay epochs through live clients and Raft
commands. It retains current/previous generations, expires older requests before
deduplication, and bounds each replay cache to 512 entries. Current/snapshot
block references survive historical metadata pruning. Pending staging has an
explicit shared cardinality limit; physical CAS reclamation remains separate.
See [live access](MESHFS-LIVE-ACCESS.md) for compatibility, expiry semantics and
limits. Candidate qualification receipts belong in the private workshop;
retention qualification does not establish global production readiness.

Check exact FIFO cardinality, preservation of evicted current/snapshot references, precise rejection of an expired pending reference, and successful publication/read of a recent block. Local state equality after an owned restart is separate from post-restart API availability. This method qualifies cardinality behavior; it does not establish full-window API ingestion,1TiBpayload throughput or fixture crash durability. Detailed receipts remain in the private workshop.


## Real ingestion evidence

End-to-end staging qualification starts with empty owned replicas and submits each distinct block through the real API and quorum. Record payload size, concurrency, elapsed budget, issued requests, hash-verified acknowledgements, uncertain/error replies and the actual local applied counts separately. A write deadline does not establish cancellation; reconcile the retained CAS and journal after stopping the owned workload. A follower's shorter applied state at stop is not by itself evidence of data loss. Partial real ingestion does not qualify the full262144-object target, and a seeded cardinality receipt does not replace that test.

## Indexed log reads and incremental applied state

Candidate0922a0b filters log ranges in SQLite, persists ordered apply deltas with
a durable progress marker, and consolidates them transactionally at snapshot
checkpoints. A separate base marker avoids parsing the previous full checkpoint
under the connection mutex. Legacy full checkpoints remain recovery bases; old
binaries that ignore the journal cannot safely downgrade a live store. Multi-entry
replication uses a10MiB entry-serialization budget with a one-command exception

JSON parsing, checkpoint migration/tail preservation/install, indivisible large
commands and durable batch recovery. Exact target-ingestion results remain scoped
receipts in the private workshop; these changes alone do not establish production
readiness. See [live access](MESHFS-LIVE-ACCESS.md).

Real ingestion acceptance still reproduces three-second uncertain outcomes after
the async storage correction. Durable reconciliation may find all issued objects;
that does not turn uncertain responses into timely acknowledgements. Keep the
latency acceptance open and correlate storage/commit/checkpoint/peer timing

artifact and environment; none establishes global production readiness.

Opt-in slow-phase diagnostics are available through `MESHFS_SLOW_PHASE_MS`
(integer1..60000, unset disables). A bounded queue feeds a dedicated stderr
writer; Raft threads never wait for output capacity. At most10000 eligible
emission attempts are admitted per process. Events distinguish admission,
blocking-pool and database-lock waits, SQL/commit, apply and snapshot phases.
Inspect sequence/drop counts before drawing conclusions from missing events.
Durations may overlap or end through cancellation; SQL scopes may include
serialization or autocommit. These observations do not change durability,
timeouts or establish a latency fix without reproducing the failure.

Threshold-filtered phase logs can miss accumulated waiting: a client deadline
may expire while shorter operations continue to finish. Retain request start,
completion and outcome times alongside phase records; do not infer one stalled
storage call merely from a deadline-shaped response or missing long span.

Finer timing distinguishes the StageChunk CAS call, metadata update, pruning,
per-entry and per-batch execution, mirror waits, and the client_write future.
The numeric count is scope-specific: batch entries, one entry, or blob-map size
for pruning; zero means unspecified. Client scopes use at least a one-second
threshold to preserve the diagnostic budget. Their total includes replication,
apply and completion waiting, so it is not a pure Raft queue measurement.
